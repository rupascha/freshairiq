# FreshAirIQ 0.26.4.6

Runtime hardening, performance and user-feedback release. Recommendations, learning and every published value are unchanged (verified: golden master 6 scenarios / 117 cycles identical, German and English).
- Less flash/SD-card wear: the learning store was rewritten as a complete JSON file in almost every 30-second cycle (128 full writes in 117 golden-master cycles). Routine learning/runtime changes are now coalesced through Home Assistant's delayed Store write (30 s, flushed on shutdown) with a hard 120 s upper bound; completed sessions, notification bookkeeping, resets and unload still save immediately.
- No more frozen entities when a weather provider hangs: the hourly `weather.get_forecasts` action now has a 10 s timeout. On timeout the state-attribute fallback and the cached forecast keep working.
- Faster coordinator cycles (about 15–20 % less CPU per cycle in the golden-master scenarios): the routine/seasonal moisture projection ensures its defaults once per room instead of once per room and 15-minute step, and `store.room()` no longer rebuilds default and opening-learning objects on every access. Results are bit-identical (randomised equivalence test against the previous algorithm).
- `store.room()` keeps a valid `opening_learning` object instead of replacing it on every access, so references held by callers can no longer silently detach.
- Diagnostics: the hourly cleanup no longer re-reads and re-parses the active day file (its mtime changes with every append); it is compacted once the day has ended.
- Learning data of rooms that were deleted from the configuration is no longer kept forever: the room is marked at the next start and its data is deleted after 30 days (kept if the room is re-added in time). Everything else on the user's side was already bounded: local diagnostics 30 days and max. 100 MB, histories 30/730 days or fixed counts.
- Tests: eight diagnostics-transport tests predated the 0.26.3 consent gate and failed; they now model an opted-in installation explicitly. New test file `tests/test_runtime_hardening_026406.py`.

Fixes and wishes from the Diagnostics Hub export of 2026-10-08:
- New (user feedback "Automationen/Trigger"): FreshAirIQ fires Home Assistant events for your own automations – `freshairiq_room_action`, `freshairiq_house_recommendation` and `freshairiq_mould_risk`. They are sent only on changes (never replayed after a restart), use the same action codes as the room "Aktion" sensor and carry a ready-to-speak sentence (`message`, e.g. "Schlafzimmer: Bitte Fenster schließen.") in the Home Assistant language, plus reasons, measurements and whether windows/fan are already working. Usable from HA automations, Node-RED (`events: all`) and Alexa announcements. New guide `docs/AUTOMATIONEN.md` (entities, events, Alexa/fan/Node-RED examples, two contacts per window, rooms without windows) and two blueprints in `blueprints/automation/freshairiq/`. FreshAirIQ itself still never switches devices.
- Change (user feedback): no mould push notification while something already works against the humidity in that room – window open, exhaust fan running, shower or its recovery phase detected, post-close buffer observation. The warning follows if the surface humidity stays high afterwards.
- Fix (GitHub #14 "Widersprüchliche Anzeige"): the Freshy view said "Ein günstigerer Zeitpunkt ist noch nicht erreicht" while listing rooms as "Lüften · 9 min" with "≈ 97 ml". The card recognised a waiting decision only from headline words ("abwarten", "nicht lüften"), but the headline intentionally varies, so this wording fell through to "recommend". The card now uses the canonical house decision (`kind`/`status` = wait). While the house waits (or keeps windows closed at night), rooms whose physics alone would allow airing show "Lüften möglich · noch warten", the duration is hidden and the amount reads "≈ 97 ml möglich". Reproduced in 14 of 117 golden-master cycles before the fix.
- Fix (GitHub #14, second part): Freshy said "4 weitere Räume ohne akuten Handlungsbedarf" while the classic view reported mould as noticeable in 6 rooms. The line now reads "… ohne akuten Lüftungsbedarf" and adds "Schimmelrisiko: N Räume auffällig" with the same criterion as the classic tile.
- Fix: deleted rooms stayed as devices ("Te", "Test" … still listed under Devices & services with all their entities). The cleanup that removes devices of deleted rooms iterated the device registry's internal mapping, which yields device IDs instead of devices; every device was skipped as "unexpected", so nothing was ever removed. It now resolves real device entries (config-entry lookup plus full registry scan). Stale room devices from earlier deletions disappear at the next start.
- Fix: a room deleted directly in Devices & services (⋮ → Delete on the room) came back after the next restart, because the room was still in the integration's own room list and was mirrored back. FreshAirIQ now remembers which room entries it created; one that the user deleted is removed from the configuration and the integration reloads right away.
- Fix (support case "Lüftungsziele priorisieren – nach dem Hinzufügen von CO₂-Sensoren lässt sich die Reihenfolge nicht bestätigen"): changing a single priority dropdown created a duplicate and the form refused to save. Choosing a goal for a position now moves it there and the others shift automatically. Room sorting works the same way.
- New (feedback): "Count residents as home at night when their phone goes off" (Residents & presence → Presence, off by default). If a tracker only switches to away during the configured night window, the person still counts as home until the night ends; residents who left before the night started stay away.
- New (feedback): several pollen sensors can be selected (e.g. one per pollen type); the highest current value counts. Existing single-sensor setups keep working unchanged.
- Checked, already fixed in the current version: "Rooms button does nothing / `this._lang is not a function`" (fixed in 0.26.2.14), font size adjustable per card area (card editor → Text sizes), laundry drying as moisture source (room → moisture sources). "Support window closes by itself" (0.26.2.8) could not be reproduced with 0.26.4.6 (support panel stays open through 25 live updates while typing); in 0.26.2.8 the `_lang` crash made the card close every open window.

## Known limits
- The coalesced persistence means that after a hard power loss (no clean Home Assistant shutdown) up to about two minutes of routine learning/runtime updates can be missing. Completed ventilation sessions and notification state are still written immediately, and a normal HA shutdown/restart flushes everything.
- Tested with the pure-logic test suite (1909 tests), the coordinator golden master in German and English, the stability, performance, migration and golden-scenario gates. New HA runtime test `ha_tests/test_room_deletion_runtime.py`. The Home Assistant runtime tests (`ha_tests`) and the pytest-cov coverage gate were not run in the build environment; please run the CI matrix before publishing.
